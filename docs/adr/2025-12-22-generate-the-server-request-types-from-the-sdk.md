# Generate the server's request types from the AWS SDK instead of writing them by hand

**Status:** Accepted

## Context

Backfilled on 2026-11-21 from `fb211ca` (#97). The commit added the HTTP `server`
front end together with `tools/generate_requests`, which writes
`server/requests.go`. The README gives the reason: the server needs input shapes
"so we can cleanly unmarshal DynamoDB JSON without the SDK's `AttributeValue`
interfaces". The generator reads the AWS SDK v2 input types and replaces
`AttributeValue` interfaces with the concrete JSON-friendly `AttributeValue` in
`server/types.go`. It reflects over the SDK input types listed in
`supportedInputs` (`reflect.TypeFor[dynamodb.PutItemInput]()` and the others),
so it depends on the SDK's struct layout. `git log -S'generate_requests'
--format='%h %ad' --date=short -- server tools | tail -1` prints
`fb211ca 2025-12-22`: this commit is where the tool first appears.

The cost of generated code showed up in #254. An aws-sdk bump (#231) added fields
to `CreateTable` and `UpdateTable` inputs "that `server/requests.go` didn't
decode, because nobody re-ran the generator. So the HTTP server dropped those
fields silently, and the parity-surface check couldn't see them either". `daed4f3` (#254) gives
the same reason for the CI step. The bump added seven fields to
`CreateTableInput` and `UpdateTableInput`; `68a935c` (#254) regenerated the file
and allowlisted those fields as out of scope in
`tools/parity-surface/allowlist.txt`. The PR body counts a 63-line diff on
`main` before the regeneration.

Facts on this branch:

- `head -1 server/requests.go` prints
  `// Code generated by tools/generate_requests; DO NOT EDIT.`
- `git grep -n 'generate_requests' -- .github/workflows` prints two lines of
  `go.yml` (a comment and the `go run ./tools/generate_requests` step that
  precedes the `git diff --exit-code server/requests.go` check from #254).
- `tools/generate_requests/generate_requests_test.go` exists, and `go.yml`
  runs `go test ./tools/...` (#254).

## Decision

`server/requests.go` is generated by `go run ./tools/generate_requests` and is
never edited by hand. Its first line is
`// Code generated by tools/generate_requests; DO NOT EDIT.`. Whoever bumps the
SDK, or changes the supported operations, regenerates it (`README.md`,
`AGENTS.md` and `docs/architecture.md`, D14, say so). CI runs the generator in
the "Generated requests are up to date" step of `.github/workflows/go.yml` and
fails when `git diff --exit-code server/requests.go` shows a change (#254).

The alternatives were considered and rejected:

- **Recorded: decode into the SDK's input types.** The README names the obstacle: the SDK's
  `AttributeValue` is an interface, so DynamoDB JSON cannot be unmarshalled into
  it directly.
- No other alternative was recorded at the time (searched: `fb211ca`, #97, #80,
  `daed4f3`, `68a935c`, #254). In particular, nothing records a comparison with
  writing the request structs by hand, or with checking freshness in a way other
  than a CI diff.

## Consequences

**Positive.** The server's input shapes follow the SDK, so a new field is one
regeneration away, and the CI check catches a stale file.

**Negative.** A stale `requests.go` silently drops fields, which is what #254
found; the CI check closes that gap only after the fact. The generator needs
the `server/types.go` `AttributeValue` and a list of supported inputs
(`supportedInputs`) that someone must extend for a new operation. Generated
output is reviewed as a diff. A new SDK field is decoded after regeneration, but
the seven fields of `68a935c` are allowlisted as out of scope
(`tools/parity-surface/allowlist.txt`), so they are decoded and not emulated.

**Neutral.** The generator's output is formatted with `go/format`. The
generator has its own test, and CI runs `go test ./tools/...`.
